# M0 — 리포 부트스트랩

아키텍처 §5 의 M0: **모노레포(worker Python + web React) · Supabase 프로젝트 ·
샘플 도면 1세트 연결**.

이 문서는 M0 에서 무엇을 만들었고, 무엇을 **실제로 검증했고**, 무엇이 아직 없는지를
적는다. 규칙 §6 — 검증 없이 완료를 주장하지 않는다.

## 1. 리포 구조

```
model3d-studio/
├─ apps/
│  ├─ web/                React 19 + Vite 8 + three.js — 뷰어·질문 카드 UI 자리
│  └─ worker/             Python 3.13 + uv — 파이프라인 워커, CLI(m3d)
├─ packages/
│  └─ contracts/          공유 데이터 계약 — JSON Schema 가 정본
│     ├─ schemas/         9개 스키마 (draft 2020-12)
│     ├─ fixtures/        TS·Python 교차 검증용 케이스
│     └─ src/             TS 타입 + 뷰 계약 수학 + 명명 규칙 + 단위 변환
├─ supabase/
│  ├─ migrations/         테이블·제약·RLS·Storage
│  └─ tests/              도메인 규칙 SQL 테스트 (+ Supabase shim)
├─ samples/               세트 정의와 매니페스트만 (도면 원본은 커밋하지 않는다)
├─ scripts/               verify-supabase.sh
└─ docs/                  정본 문서
```

## 2. 규칙을 코드로 강제한 지점

지식베이스의 규칙은 문서로만 두면 지켜지지 않는다. M0 에서 **기계가 강제**하도록
옮긴 것들:

| 규칙 | 강제 수단 | 위치 |
|---|---|---|
| §1 mm↔m 변환은 한 곳에서만 | ESLint `no-restricted-syntax` 가 `*1000`·`/1000` 을 차단, pytest 가 `units.py` 밖의 변환식을 검출 | `eslint.config.js`, `test_units.py` |
| §1 방위 가정은 뒤집기 검증 등재 | JSON Schema `if/then` + pydantic validator | `coordinate_system.schema.json`, `models.py` |
| §2 근거 없는 수치 반려 | `source_sheets` `minItems: 1` | `ssot_item.schema.json` |
| §2 파생 계산은 검산 동반 | `derived: true → derivation·cross_check 필수` | 같은 파일 `allOf` |
| §2 검산 FAIL 은 확정 불가 | `if cross_check.result=FAIL then status ≠ confirmed` | 같은 파일 |
| §3 중요 치수 교차 확인 | `cross_source_confirmed → source_sheets ≥ 2` | 같은 파일 |
| §3 애매값은 추정 확정 금지 | ambiguity 구조 자체가 선택지를 강제 | `ambiguity.schema.json` |
| §4 한 질문 = 한 요소 | `item`·`question` 단수 필드 | 같은 파일 |
| §4 질문에 크롭 동반 | `sheet_refs` `minItems: 1`, `bbox_px` 필수 | 같은 파일 |
| §4 선택지 2~4개, 권장안 첫 번째 하나 | `minItems/maxItems` + `prefixItems[0].recommended=true` + `items.recommended=false` | 같은 파일 |
| §4 "모르겠다"는 잠정 기록 | `choice=unknown → provisional=true` | `decision.schema.json` |
| §5 부재 명명 규칙 | 정규식 — 스키마·TS·Python 세 곳의 문자열 일치를 테스트가 강제 | `member.schema.json`, `memberName.ts`, `member_name.py` |
| §6 허용오차 명시 | `tolerance` 필수 필드 | `verification_report.schema.json` |
| §6 재실측 기대값은 사양서에서 | `stage=independent_remeasure → expected_derived_from ≠ builder_code` | 같은 파일 |
| §7 뷰 계약 왕복 검산 | R1·R2·R3 구현 + 양 언어 교차 검증 | `viewContract.ts`, `view_contract.py` |
| §8 자기 검증 금지 | `builder_agent == performed_by` 이면 거부 | `models.py` |
| §3 표제란 대조 | `titleblock_match` 필드 + 파일명/표제란 도면번호 분리 | `sheet.schema.json` |
| §3 키플랜 라벨 오탐 방지 | coverage `source` 에 `keyplan_label` 을 넣지 않음 | 같은 파일 |
| CLAUDE.md §3 비밀키 | 브라우저가 service key 형태를 거부, 워커는 `SecretStr` | `env.ts`, `config.py` |

이 표의 각 항목에는 **"거부되어야 하는 문서"** 픽스처가 붙어 있고,
TS(ajv)·Python(jsonschema+pydantic) 양쪽이 실제로 거부하는지를 테스트가 확인한다.

## 3. 기술 선택과 근거

측정하지 않은 선택은 적지 않았다.

### TypeScript 6.0.3 (7.x 아님)
npm `latest` 는 7.0.2 지만, `typescript-eslint@8.68.0` 의 peer 는
`typescript: ">=4.8.4 <6.1.0"` 이다(레지스트리 조회 확인, canary 도 동일).
TS 7 을 쓰면 린트가 통째로 죽는다. 6.0 은 typescript-eslint 가 명시적으로 지원한다.

### three.js 직접 사용 (React Three Fiber 아님)
`@react-three/fiber@9.7.0` 의 peer 는 `react: ">=19 <19.3"` — 우리 React 버전을
고정해 버린다. 반면 필요한 것은 (1) 정사영 카메라 프러스텀 계산, (2) 뷰 계약
좌표 변환, (3) GLB 노드 트리 순회로 전부 **명령형**이라 R3F 의 선언적 재조정기가
이득을 주지 않는다. 얇은 React 래퍼(`GlbViewer.tsx`)로 감쌌다.

### Python ≥ 3.12 (`.python-version` = 3.13)
`numpy 2.5.2` 와 `scipy 1.18.1` 의 `requires_python` 이 `>=3.12` 다(PyPI 조회 확인).
컨테이너 기본 파이썬은 3.11 이라 부족하므로, uv 가 인터프리터를 받아오게 했다.

### JSON Schema 가 정본 (pydantic 아님)
pydantic 을 정본으로 두면 `@model_validator` 로 쓴 규칙이 `model_json_schema()` 에
**나오지 않는다**. 그러면 TS 도, Agent SDK 구조화 출력 스키마도 규칙을 보지 못한다.
조건부 규칙(`if/then`)을 표현할 수 있는 층은 JSON Schema 뿐이므로 그쪽을 정본으로 삼았다.

**남은 한계(의도적)**: `packages/contracts/src/types.ts` 의 TS 타입은 손으로 쓴
**형상 미러**다. 스키마 ↔ pydantic 드리프트는 `test_model_fields_match_schema_properties`
가 기계적으로 잡지만, 스키마 ↔ TS 타입은 잡지 못한다(TS 타입은 런타임에 지워진다).
그래서 **신뢰 경계(에이전트 출력·API 입력·DB 적재)에서는 생성/수기 타입이 아니라
런타임 JSON Schema 검증(TS=ajv, Python=jsonschema)을 통과시킨다.** 타입은 편의일 뿐이다.

### PDF 는 pypdfium2 (PyMuPDF 아님)
아키텍처 §2 는 PyMuPDF 를 적었지만, PyMuPDF 는 **AGPL-3.0 / Artifex 상용 듀얼
라이선스**다. 도면 PDF 래스터화를 서버에서 수행하는 SaaS 는 AGPL 의 네트워크 배포
조항에 걸려 상용 라이선스가 필요해질 수 있다. `pypdfium2 5.13.0` 은
BSD-3-Clause / Apache-2.0 이라 제약이 없고, 아키텍처 §3 의 **"라이선스 프리 원칙"**
과도 일치한다. 래스터화(`page.render`)와 텍스트 추출(`get_textpage`) 모두 실제 PDF 로
동작을 확인했고 회귀 테스트를 남겼다(`test_pdf_backend.py`).
아키텍처 문서가 병기한 `pdftoppm`(poppler-utils)은 외부 프로세스 경로로 여전히 유효한 대안이다.

### three.js 직접 사용을 유지 (R3F 재검토 결과)
리서치에서 R3F 를 실측 후 권장했으나, 그 권장안조차 react 를 `~19.2.x` 로 고정해야
한다는 결론이었다(R3F 9 의 peer `react: ">=19 <19.3"`). M0 시점에 React 마이너를
잠그는 비용이 R3F 의 이점(선택·하이라이트의 React state 연동)보다 크다고 보아
raw three.js 를 유지했다. 필요해지면 M2 에서 R3F 를 추가하는 편이 역방향보다 싸다.

### 워커 컨테이너에는 Node 22 가 필요하다
`claude-agent-sdk` 는 순수 파이썬 패키지가 아니다 — 런타임에 Node CLI
`@anthropic-ai/claude-code` 를 **subprocess 로 띄운다**(node ≥ 22 요구).
파이썬만 있는 이미지로 워커를 배포하면 런타임에 실패한다. 배포 이미지에 Node 22 를
포함시켜야 한다.

### 샘플 세트는 매니페스트만 커밋
참조 원본은 사용자 로컬에만 있고 읽기 전용이다(CLAUDE.md §2). 도면 PDF·DWG 는
커밋할 수 없다. 그래서 "무엇이 있어야 하는가"(경로·크기·SHA256·역할)만 커밋하고,
실제 파일은 `.gitignore` 된 작업 디렉터리로 `ingest` 한다. 원본이 없는 환경에서는
`verify` 가 **조용히 성공하지 않고** 그 사실을 보고한다.

### `@model3d/contracts/node` 서브패스 분리
스키마 로더가 `node:fs` 를 쓰는데, 이를 패키지 메인 진입점에서 재수출하니
브라우저 번들에 node 내장 모듈이 끌려들어갔다(빌드 경고로 확인). node 전용
진입점으로 분리해 번들에서 제거했다.

## 4-1. 남은 리스크 (M1 착수 전 확인할 것)

리서치에서 실측으로 드러난, 지금은 막지 않았지만 알고 있어야 하는 것들:

- **`readings.source_sheets` 는 배열이라 FK 를 걸 수 없다.** "존재하지 않는 도면번호를
  근거로 든 수치"를 DB 가 막지 못한다. 워커 측 검증기나 정합성 쿼리로 보완해야 한다.
- **승인 게이트 트리거는 렌더 3종의 *존재*만 본다.** 맥락 렌더에 인접 구간 스텁이
  실제로 들어갔는지는 DB 가 판정할 수 없다 — 규칙 §6-3 의 그 부분은 사람/에이전트 판정에 남는다.
- **`decision.choice` 의 상한이 3 으로 고정**되어 있다. 진짜 제약은 `choice < len(options)`
  인데 options 가 다른 문서에 있어 JSON Schema 로 교차 참조가 불가능하다. 애플리케이션 층에서 막아야 한다.
- **`readings` 가 `(project_id, item)` 유니크**다. 부재마다 반복되는 항목명(예: 부재별 '두께')을
  쓰려면 M1~M2 에서 유니크 키를 재검토해야 한다.
- **`project_members` 에 owner 가 0명이 되는 상황을 DB 가 막지 않는다.** 멤버 관리 UI 를
  붙일 때 '마지막 owner 삭제 금지' 트리거가 필요하다.
- **로컬 검증은 PostgreSQL 16 + 자체 shim 위에서 했다.** 실 Supabase(PG 17)의 `auth.uid()`
  구현과 `storage.objects` 컬럼 구성은 shim 과 다르다. 실제 프로젝트에 처음 적용할 때 재확인이 필요하다.
- **`claude-agent-sdk` 는 0.x** 다. API 가 굳지 않았으므로 상한을 두는 편이 안전할 수 있다.

## 5. 아직 없는 것

M0 는 **부트스트랩**이다. 파이프라인 8단계는 하나도 구현되지 않았다.

- [2] 변환·정규화, [3] 카탈로그·분류 → **M1**
- [4] 병렬 판독, [5] 질문 루프 → **M2**
- [6] 병렬 모델링, [7] 3중 검증, [8] 산출·연동 → **M3**

또한:
- Supabase 프로젝트는 **스키마만** 준비되어 있다. 실제 프로젝트 생성·마이그레이션
  적용은 사용자가 자기 계정에서 해야 한다 (§6 참조).
- 샘플 도면 세트의 **실제 파일은 이 리포에 없다**. 원본이 있는 머신에서
  `m3d samples ingest ab1_p4p5` 를 실행해야 매니페스트가 채워진다.
- 웹 화면은 헬스체크와 빈 뷰어뿐이다. 질문 카드 UI 는 M2 다.
- 에이전트 프롬프트는 아직 없다. 계약(스키마)만 준비되었다.
- **CI 워크플로가 아직 켜져 있지 않다.** 파일은 `ci/workflows/ci.yml` 에 있고 내용은
  로컬에서 전부 실행해 확인했지만, 커밋에 쓰인 GitHub App 에 `workflows` 권한이 없어
  `.github/workflows/` 아래로 push 할 수 없었다(git·Contents API 양쪽 거부).
  `ci/README.md` 의 한 줄 명령으로 사람이 옮겨야 한다.

## 6. Supabase 프로젝트 연결

1. supabase.com 에서 프로젝트를 만든다.
2. 루트 `.env` 에 값을 채운다 (`.env.example` 참고). **커밋 금지.**
3. 마이그레이션을 적용한다.

```bash
# Supabase CLI 사용 시
supabase link --project-ref <ref>
supabase db push

# 또는 psql 로 직접
for f in supabase/migrations/*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"; done
```

`supabase/tests/00_supabase_shim.sql` 은 **로컬 검증 전용**이다 —
`auth`·`storage` 스키마를 흉내내므로 실제 Supabase 에는 적용하지 않는다.

4. 확인: `uv run --project apps/worker m3d doctor`
